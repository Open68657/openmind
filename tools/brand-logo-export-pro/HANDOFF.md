# Handoff

This is the complete source of Brand Logo Export Pro. It is the whole app: there
is no backend, no API key, no database. Everything runs in the browser.

## Start here

```
npm install
npm run dev          # http://localhost:3010
```

`npm run build` produces `dist/`, a static folder you can host anywhere.
The `--base=./` in the build script keeps asset paths relative, which is what
GitHub Pages needs when it serves from a subpath.

## What is in the box

| path | what it is |
|---|---|
| `src/App.tsx` | the entire app: 4 screens, SVG handling, PDF and ZIP generation |
| `src/cmykLut.ts` | 33³ lookup tables baked from real Adobe ICC profiles. Generated, do not hand-edit |
| `src/constants.ts` | palette defaults, margins, profile list |
| `scripts/build_cmyk_lut.py` | regenerates `cmykLut.ts` (Python + PIL/littleCMS) |
| `preview.sh` | builds and stages the production build to `/tmp` for a local check |
| `publish.sh` | builds and pushes `dist/` to the GitHub Pages repo |

`node_modules/` and `dist/` are not included. Both are regenerated by the two
commands above.

## Before you publish

`publish.sh` is hardcoded to push to `Open68657/brand-logo-export`, which serves
https://open68657.github.io/brand-logo-export/. To publish somewhere else, change
`PAGES_REPO` and the `git config user.name` / `user.email` lines near the bottom.
Only the build ever gets pushed there, never this source tree.

## Decisions that are already settled

Worth knowing before you "fix" any of these:

- **`cmyk/` contains a vector PDF and nothing else.** A browser canvas can only
  encode sRGB, so a JPEG written from it is RGB no matter what the folder is
  called, and rasterizing the PDF does not change that. The JPEG lives in `rgb/`,
  where it is honest, and it stays there so people without design software can
  still use the colour combination.
- **Pantone names come only from the user**, through the per-colour field or a
  parsed guidelines document. Never derive one from RGB. That needs the licensed
  colour books, and a guess shows up on press.
- **The combination dropdowns are palette-only** by request. The free colour
  picker exists on the palette screen and only there, so combinations stay on
  defined brand colours.
- **Live `<text>` in an uploaded SVG blocks the whole flow**, not just the export.
  jsPDF silently substitutes Helvetica, so the shape would depend on the reader's
  fonts. The fix is Create Outlines in Illustrator and re-upload.
- **Spot colours are written by hand into the PDF.** jsPDF has no Separation
  support, so `injectSpotColorSpaces` writes the operators into the content
  stream and splices the colour space into the page resources. That shifts every
  byte offset, which is why the xref table is rebuilt and spot PDFs are generated
  uncompressed. Read that function before touching the PDF path.

## Known rough edges

- `vite.config.ts` still defines `process.env.GEMINI_API_KEY` from the original
  scaffold. Nothing reads it. Same for `.env.example`.
- `npm run lint` (`tsc --noEmit`) reports three long-standing errors in
  `App.tsx`: the `?raw` worker import, which tsc cannot resolve without Vite's
  client types, and two `unknown` values in the file-drop handler. The build uses
  esbuild and does not typecheck, so none of them affect the output. They were
  there before this handoff.
- The main bundle is about 1.5MB. It is one file by choice, not by accident, but
  code splitting is the obvious next win if load time ever matters.
- The UI is RTL Hebrew. Numbers and filenames are forced `dir="ltr"`, and a
  continue arrow is `←` while back is `→`. Keep an arrow glyph where it sits in
  the string; bidi moves it to the right edge on its own.
